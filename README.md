# BYTE BACK 방어전 시작 틀 R5

이 저장소는 1단계에서 학생 본인이 GitHub 저장소와 Vercel 배포를 만드는 출발점입니다. 포함된 메모 네 건은 가상 자료입니다. 실제 학생 자료, 토큰, 비밀키를 넣지 마세요.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 **Deploy** 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 **본인 계정의 Public 저장소**인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. `/data.json`에는 같은 가상 메모가 공개됩니다. 이 공개 상태를 확인하는 것이 1단계의 출발점입니다. 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 이전 제출 묶음 방식의 자리표시자입니다. 1단계에서는 학생이 편집하지 않습니다. 2단계 이후 코딩 도구가 필요한 설정과 보호 기능을 단계별로 작성합니다. `npm run bundle`과 `bundle-notes.json`도 1단계의 세 걸음에는 포함되지 않습니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 저장소의 `src/attack-check.mjs`는 실제 배포가 된 뒤 `/data.json`을 비로그인으로 요청해 공개 가상 메모의 확인 표시를 읽습니다.

## 다음 단계의 코딩 도구에 전달할 규칙

[AGENTS.md](AGENTS.md)를 먼저 읽히고 한 번에 한 제작 단위만 요청하세요. 2단계부터는 자료 보호를 구현할 때 `public/data.json`을 복사하는 1단계 빌드 흐름도 함께 바꿔야 합니다. 3단계 이후의 로그인, 허용 경로, 5단계의 원본 API 주소, 6단계 이후 정책 규칙은 해당 단계 원고와 계약에 맞춰 추가합니다. 비밀번호·토큰·서버 전용 키·실제 학생 기록을 코드, Git, 제출 묶음에 넣지 않습니다.

`src/decider.mjs`와 `src/detect.mjs`의 로컬 시험은 반 엔진이나 운영 심판의 결과가 아닙니다. 1단계 이후 제출 묶음 계약 `aleph.defense.submission.v2`는 `scripts/bundle.mjs`에 남아 있으며, 코딩 도구가 해당 단계의 최신 배포 주소와 Git 원격을 맞춘 뒤 사용합니다.

## 2단계 제작 진행

가상 메모 네 건을 학습용 Supabase의 byteback_notes 테이블로 옮겼습니다.
현재 data.json과 public/data.json에는 빈 notes 배열만 둡니다.
화면은 /api/notes를 통해 메모를 읽습니다.
서버는 SUPABASE_URL과 SUPABASE_SECRET_KEY 환경변수를 사용합니다.
키는 브라우저 코드, API 응답, 로그에 출력하지 않습니다.

아직 /api/notes에는 로그인 검사가 없어 누구나 호출할 수 있습니다.
DB의 RLS와 anon·authenticated 권한 제한은 공개 서버 API의 접근 제한을 대신하지 않습니다.
이전 공개 Git 커밋과 이전 배포에는 메모가 남아 있을 수 있습니다.
과거 노출이 해소된 상태로 간주하지 않습니다.

로컬 정적 빌드 확인: npm run build -- --local
이 명령은 실제 DB 연결이나 Vercel 배포 성공을 확인하지 않습니다.
2단계 배포와 제출 묶음 자기 점검을 완료했습니다.

### 2단계 확인 절차

- 최신 작업 파일에서 가상 메모 본문과 비밀값 형태를 검색합니다.
  검색 시 값 자체는 출력하지 않고 해당 파일 이름만 기록합니다.
- 로컬 빌드 뒤 public/data.json이 빈 notes 배열인지 확인합니다.
- 배포 뒤 /data.json의 빈 배열과 /api/notes의 가상 메모 네 건을 확인합니다.
- 화면에서 네 카드가 표시되는지 확인합니다.
- /aleph.json의 단계, 저장소, 커밋을 실제 배포와 대조합니다.
- npm run bundle의 API 점검은 학생의 자기 점검이며 심판 판정이 아닙니다.
- 최신 파일 검사로 이전 공개 커밋과 이전 배포의 노출까지 해소되지는 않습니다.

## 3단계 저장점

Supabase Auth 이메일·비밀번호 로그인과 로그아웃을 사용합니다.
서버는 수정하지 않은 src/verify-login.mjs로 요청 토큰을 검증합니다.
로그인하지 않았거나 토큰 검증에 실패하면 메모 없이 401로 거부합니다.
서버 전용 키는 Vercel 환경변수에만 두며 브라우저에는 공개용 키만 둡니다.

로그인 계정은 가상 메모를 추가·수정·삭제할 수 있습니다.
추가 시 owner_id는 서버가 검증한 사용자 ID로 저장합니다.
DB의 메모 ID는 UUID이며 기존 가상 메모 네 건은 A 계정에 연결했습니다.
목록은 로그인 계정의 메모 배열이고 단일 메모는 {id,title,body}입니다.
실제 경로는 aleph.config.json의 allowedRoutes에 기록했습니다.

단일 메모 조회·수정·삭제의 소유자 검사는 아직 없습니다.
따라서 로그인한 B가 A의 메모 ID를 알면 접근할 수 있습니다.
이 약점은 4단계에서 막습니다. 이전 공개 커밋·배포 이력도 남습니다.

다시 실행: npm run build -- --local
Vercel에서는 환경변수 SUPABASE_URL과 SUPABASE_SECRET_KEY가 필요합니다.
자기 점검: 저장점 커밋과 실제 배포 완료 후 npm run bundle
토큰 없는 조회·추가·수정·삭제와 위조 토큰 요청의 거부를 점검합니다.
정상 A 로그인과 메모 CRUD는 배포 화면에서 별도로 확인합니다.
만료 토큰과 다른 서비스 토큰의 개별 공격 점검은 아직 미실행입니다.
자기 점검은 운영 심판 판정이 아닙니다.

## 4단계 저장점

서버는 검증된 사용자 ID로 모든 메모 조회·수정·삭제를 제한합니다.
추가 시 소유자는 서버가 지정하고, 요청 본문의 owner_id 등 허용되지 않은 필드는 거부합니다.
수정은 title과 body만 바꾸므로 소유자는 변경할 수 없습니다.
타인 메모는 없는 메모와 동일하게 자료 없이 404로 응답합니다.
이 절의 현재 동작은 앞선 3단계의 소유자 검사 미구현 기록을 대체합니다.

기존 A 가상 메모 네 건을 보존하고 B 시험 메모 한 건을 준비했습니다.
학습 DB의 RLS를 켜고 anon 권한을 회수했습니다.
authenticated에는 SELECT·INSERT·UPDATE·DELETE만 허용했습니다.
네 RLS 정책은 auth.uid()와 owner_id를 비교합니다.
UPDATE는 USING과 WITH CHECK를 모두 사용합니다.
실제 권한과 네 정책 조건은 SQL Editor에서 확인했습니다.

서버 전용 키를 사용하는 앱 API는 자체 소유자 검사를 수행합니다.
서버 전용 키 접근에 RLS가 대신 적용된다고 간주하지 않습니다.
직접 Data API는 공개용 키의 anon 요청으로 자기 점검합니다.
authenticated 역할의 직접 Data API 접근 시험은 미실행입니다.

다시 실행: npm run build -- --local
배포 완료 후 자기 점검: npm run bundle
A/B의 정상 CRUD와 타인 메모 접근 거부는 별도로 확인해야 합니다.
현재 4단계 배포와 A/B 교차 접근 시험은 아직 미실행입니다.
이전 공개 커밋과 배포의 노출 이력은 남아 있습니다.

## 5단계 저장점

브라우저의 메모 조회·추가·수정·삭제는 Vercel 서버 API만 사용합니다.
Supabase Auth 로그인·로그아웃 호출은 유지합니다.
메모 테이블의 PUBLIC·anon·authenticated 직접 권한을 회수했습니다.
권한 회수 전후 실제 권한을 확인했으며 회수 후 A의 정상 CRUD와 로그아웃도 확인했습니다.
기존 RLS 정책과 메모, 서버 전용 역할의 권한은 보존했습니다.
서버 API는 검증된 로그인과 메모 소유자를 계속 검사합니다.
원본 자료 경로는 aleph.config.json의 originalApiUrl에 쿼리 없이 기록했습니다.

다시 실행: npm run build -- --local
배포 완료 후 자기 점검: npm run bundle
원본 Data API의 공개용 키 요청은 거부되어야 합니다.
authenticated 직접 Data API 요청의 개별 시험은 아직 미실행입니다.
5단계 배포 후 B의 상대 메모 접근 거부는 재확인이 필요합니다.
이전 공개 커밋과 배포의 노출 이력은 남아 있습니다.

### 5단계 완결성 보완

- 배포 aleph.json에 allowedRoutes를 포함합니다.
- 첫 화면에 X-Content-Type-Options: nosniff 헤더를 설정합니다.
- 화면의 Supabase 공개 키와 SDK 연결을 제거했습니다.
- 로그인·갱신·로그아웃은 /api/auth에서 공식 SDK로 처리합니다.
- 서버 환경변수 SUPABASE_PUBLISHABLE_KEY가 필요합니다.
- 메모 API의 로그인·소유자 검사와 DB 권한 제한을 유지합니다.
- 로그인 세션은 현재 탭의 sessionStorage에 저장합니다.
- 로컬 빌드와 기존 테스트는 통과했습니다.
- 새 로그인 흐름과 보안 헤더의 실제 배포 확인은 아직 미실행입니다.

## 보너스 xdr-01 저장점

공식 학습용 경보를 읽고 MITRE T1110 기반 패턴으로 분류합니다.
decide.mjs는 import, 파일 접근, 네트워크 없이 경보 하나를 판단합니다.
읽기 모듈은 28건을 28줄로 변환했습니다.
시험 결과: block 10건, alert 9건, record 9건.
정상으로 검토한 9개 시험 이벤트의 block은 0건입니다.
respond.mjs는 근거 경보 ID와 15분 만료가 있는 차단 후보를 생성합니다.
알림 로그와 차단 후보 파일은 Git에 포함하지 않습니다.
공격 주소 후보 일치, 정상 주소 불일치, 만료 후 불일치를 확인했습니다.
현재 ZTNA 계약에 검증된 출발 IP가 없어 실제 판정기 연결은 미완료입니다.
기존 src/decider.mjs와 자료실의 인증·소유자 검사는 변경하지 않았습니다.
시험 경보 결과는 실제 Wazuh 탐지나 운영 접속 차단의 증거가 아닙니다.

다시 실행: npm run xdr:run -- brute-force

## 6단계 판정기 확인

별도로 설치할 접속 프로그램은 없습니다. 로컬 판정기 연습은 다음 순서로 확인합니다.

1. `npm run decider:test`를 실행합니다.
2. 등록 기기의 정상 요청이 `allow`로 판정되어 통과하는지 확인합니다.
3. 미등록 기기의 가상 요청이 `deny`, 사유 코드 `device_not_registered`로 판정되어 통과하는지 확인합니다.
4. 미등록 기기 공격은 심판이 담당합니다. 이 로컬 연습은 심판 판정이나 실제 접속 공격 시험이 아닙니다.

## 7단계 추가 확인

판정 요청 계약에는 가명 `subjectId`와 `stepUp.verified`·`stepUp.authAgeSeconds`가 있습니다.
하지만 새 로그인 시각을 같은 `subjectId`에 명시적으로 연결하는 필드는 없어, 실제 로그인 주체 재확인과 자료 차단은 아직 미실행입니다.

등록 기기에서 평소와 다른 시각, 낯선 네트워크, 최근 다량 읽기 신호가 함께 있는 가상 사건만 `step_up`으로 보냅니다.
정상 사건은 `allow`, 미등록 기기는 기존 규칙대로 `deny`입니다.
가상 추가 인증 뒤 같은 요청을 다시 판정하는 흐름만 연습하며, 실제 자료 차단을 확인한 것으로 간주하지 않습니다.

다시 실행: `npm run decider:test`
제출 묶음 자기 점검: `npm run bundle`

## 8단계 자료 구역 확인

기존 메모 ID와 `/api/notes/:id` 주소는 유지합니다. 서버는 검증된 로그인 사용자와 메모의 저장된 `owner_id`를 다시 비교합니다.

1. `node --test test/resource-identity.test.mjs test/resource-access.test.mjs`를 실행합니다.
2. `GET`·`PUT /api/notes/:id` 및 호환 notes 단건 route만 판정기 허용 후보입니다. 실제 소유자 비교는 API가 수행하고, 다른 사용자의 메모 직접 API 요청은 자료 없이 404로 거부됩니다.
3. 단건 ID는 한 segment이며 `all`·`export`는 제외합니다. Collection 경로, query가 있는 요청, 단건 POST·PATCH·DELETE 및 collection 쓰기는 거부합니다. 공지는 별도 구역으로 식별해 GET만 허용하고 쓰기는 거부하며, 강사 자료 구역은 모든 접근을 거부합니다.
4. service·method·실제 경로·route가 정확히 맞지 않으면 `resource_unknown`으로 거부합니다. 요청 본문의 `role`은 권한 근거로 사용하지 않습니다.

자기 점검은 로컬 가상 자료를 사용하며 실제 강사 권한이나 운영 API 판정의 증거가 아닙니다.

## 복구 절차

### 1. 백업 검증

복원 직전에 저장해 둔 안전 정책 사본과 비공개 메모 백업 사본을 다시 읽습니다.

다시 읽은 사본에서 버전과 이번 복원으로 바뀔 항목을 확인하고, 실제 복원보다 먼저 화면에 보여 줍니다.

- 복원에 사용할 안전 정책 사본의 버전 번호
- 이번에 복원할 메모의 ID
- 변경 범위: 지정한 메모 한 건의 `title`, `content`
- 메모 사본에 저장된 소유자
- 메모 사본에 저장된 내용 SHA-256

정책 사본이 없거나 검증된 버전·해시와 다르면 복원하지 않고 멈춥니다.
지정한 메모의 백업 사본이 없으면 복원하지 않고 멈춥니다.
다시 읽은 메모 사본의 내용 SHA-256이 저장 당시 `content_sha256`과 다르면 검증 실패로 처리하고 복원하지 않습니다.
처음 읽은 사본과 복원 직전에 다시 읽은 사본의 ID·소유자·내용 해시가 하나라도 다르면 복원하지 않고 멈춥니다.

백업 검증에 성공했을 때만 다음 단계인 「2. 한 건 복원」으로 넘어갑니다.
실제 운영 정책 자체는 이 절차에서 변경하지 않습니다.

### 2. 한 건 복원

- 서비스: `restore`
- 경로: `POST /api/restore/:noteId`
- 대상: 검증된 시험 계정 B의 비공개 백업 메모 중 지정한 한 건

복원 전에는 요청한 `noteId`와 다시 읽은 사본의 ID가 같은지 확인하고,
검증된 로그인 사용자의 소유자 ID와 사본의 소유자가 같은지 확인하며,
사본 본문의 SHA-256을 다시 계산해 저장된 `content_sha256`과 비교합니다.

세 값 가운데 하나라도 맞지 않거나 백업 검증이 실패하면 복원하지 않습니다.
검증에 성공한 경우에만 DB 복구 함수로 지정한 메모 한 건을 복원합니다.

복원 뒤에는 RPC 결과만 믿지 않고 실제 저장된 메모 한 건을 다시 읽어
ID·소유자·내용 SHA-256이 검증한 사본과 같은지 다시 확인합니다.
다르면 복구 성공으로 기록하지 않습니다.

다른 메모는 변경하지 않고 기존 감사 기록도 삭제하거나 덮어쓰지 않습니다.
비공개 백업 본문은 Public Git 저장소에 넣지 않습니다.

## 11단계 저장점

설치형 웹앱용 `manifest.webmanifest`를 연결하고 BYTE BACK 자료실을 standalone 웹앱으로 열 수 있게 했습니다.
앱 설치 여부는 기기 승인으로 취급하지 않으며 화면에도 서버의 기기 승인 확인이 별도로 필요하다고 표시합니다.
오프라인에서는 보호 자료를 열 수 없고 서버 연결 뒤 승인 상태를 다시 확인하도록 안내합니다.

로그인 뒤에도 바로 보호 자료를 요청하지 않습니다.
화면에서 기기 승인을 요청하면 서버는 승인 요청만 기록하고,
서버가 관리하는 `principal_bindings`에서 현재 기기의 승인 상태를 별도로 확인합니다.
기기 개인키·승인 인증서·로그인 토큰은 브라우저 저장소에 기록하지 않고 현재 페이지 메모리에만 둡니다.
승인이 끝나기 전에는 메모 편집기와 보호 자료를 표시하지 않습니다.

승인된 기기의 보호 요청은 HTTP method, 실제 요청 path/query, 요청 body의 SHA-256,
승인 인증서, 요청 시각, nonce를 함께 서명합니다.
서버는 11단계부터 이 서명이 없거나 틀리면 `app_proof_invalid`로 거부합니다.
따라서 서명 뒤 요청 경로를 바꾸거나 PUT 본문을 바꾸면 기존 서명과 맞지 않아 거부됩니다.
기존 로그인·메모 소유자 격리·1~10단계 보호와 복구 기능은 그대로 유지합니다.
